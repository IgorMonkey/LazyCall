# Рабочий процесс разработки

[English](DEVELOPMENT_WORKFLOW.md)

В LazyCall используется GitHub Flow: `main` — общая ветка интеграции, работа идёт в короткоживущих ветках. На этом этапе нет ни ветки `develop`, ни release-веток.

## Ветки и pull request

Создавайте ветку от актуального `main`, делайте сфокусированный pull request и удаляйте ветку после merge.

- Для обычной работы используйте `feat/...`, `fix/...` или `docs/...`. Если точнее описывает изменение, подходят `refactor/...`, `test/...`, `build/...`, `ci/...` и `chore/...`.
- Для работы coding-агента используйте префикс ветки `codex/...`.
- Перед merge pull request обязан пройти **Build and test on Windows**. Он вливается в `main` через squash; не вливайте ветку с несвязанными изменениями или нерешённым замечанием ревью.
- Pull request Dependabot — исключение из соглашений об имени ветки и Conventional Commit-заголовке. CI для него всё так же обязателен, а auto-merge эта политика не включает. Решение о merge любого pull request принимает мейнтейнер.

Используйте Conventional Commit-style заголовок PR: `feat:`, `fix:`, `docs:`, `refactor:`, `perf:`, `test:`, `build:`, `ci:` или `chore:`. Breaking change отмечается `!` после типа, например `feat!: replace meeting export schema`, либо разделом `BREAKING CHANGE:` в теле PR. В PR описываются влияние на пользователя, проверка и необходимые шаги миграции.

Это соглашение проекта поверх модели GitHub Flow; см. [документацию GitHub Flow](https://docs.github.com/en/get-started/using-github/github-flow).

## Версии и release train

`package.json` — единственный источник версии приложения. Release-тег всегда равен `v<версии из package.json>` и указывает ровно на коммит, для которого выпускаются assets.

Первый публичный train — `0.3.5-alpha.1`. Более ранние сборки `0.3.4` были локальными preview, поэтому публичная линия не начинается с `0.1`. Планируемая последовательность:

```text
0.3.5-alpha.1 → 0.3.5-alpha.2 → … → 0.3.5-beta.1 → … → 0.3.5-rc.1 → … → 0.3.5
```

Исправления внутри train повышают prerelease-номер, например до `0.3.5-alpha.2`. После стабильной `0.3.5` совместимое исправление получает `0.3.6`, а совместимая функция — `0.4.0`. Пока major равен нулю, breaking change также повышает minor и обязан иметь явные заметки миграции: например, после `0.3.x` это `0.4.0`. Начиная с `1.0.0`, SemVer использует major для breaking changes, minor для обратно совместимых функций, patch для обратно совместимых исправлений.

Совместимость включает проекты пользователя, сохранённые настройки, расшифровки, экспорты и контракт провайдера, а не только API исходного кода. Изменение, которое делает что-то из этого нечитаемым, меняет смысл данных или молча меняет поведение провайдера, считается breaking, если нет документированной совместимой миграции.

Версия в package, заголовок PR, проверка release-тега и Windows CI делают соглашения проверяемыми. Они ничего не публикуют автоматически: ручной release workflow создаёт только артефакты для ревью. После проверки мейнтейнер вручную публикует GitHub Release из точного коммита с тегом, соответствующими assets и `SHA256SUMS.txt`. Опубликованные теги и assets неизменяемы: не перетегируйте, не заменяйте и не перезаписывайте их; вместо этого выпустите исправляющую версию.

Интерпретация версий следует [спецификации Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html).
